# 실험 006 - Spike Test

## 목적

경기 시작처럼 트래픽이 **갑자기 올랐다가 다시 줄어들 때** 앱이 죽지 않는지, **줄어든 뒤 회복하는지** 확인한다.

## 현재 문제

Load/Stress([005-load-test.md](005-load-test.md))에서 지속 처리량 천장은 약 500 start RPS, 병목은 Hikari 40이었다.
Spike는 같은 천장 위로 순간적으로 밀어 회복을 본다.

## 가설

5,000 RPS는 이 노트북 단일 프로세스에서 소화되지 않는다.
에러가 나더라도 부하를 500으로 되돌리면 풀 대기가 빠지고, 프로세스 CPU/health는 돌아올 것이다.
500 자체가 천장 근처라, 피크 직후 500으로 내려도 지연은 바로 안 좋아질 수 있다.

## 테스트 환경

005와 동일. 스크립트 `load-test/k6/playback-spike.js`. 시작 전 `playback_session` TRUNCATE.

```text
20s  → 500
1m   → 500     (피크 전)
10s  → 5,000
30s  → 5,000   (피크)
10s  → 500
1m   → 500     (회복)
15s  → 0
```

maxVUs 1200, start timeout 10s.

## 결과

### 전체

| 지표 | 값 |
| --- | ---: |
| iterations | 92,098 |
| 평균 iteration rate | 449.2 /s |
| dropped_iterations | 182,651 |
| start error | 0.00% (끝부분 timeout 소수, http_req_failed 0.002%) |
| start p50 | 993.53 ms |
| start p95 | 1,647.00 ms |
| start p99 | 2,421.61 ms |
| Hikari active/pending max | 40 / 159 |
| Hikari timeout | 0 |
| process CPU max | ~21% |

### 구간

**피크 전 500 (약 0:20–1:20)**  
k6 VU가 20~50까지 떨어지며 500 /s를 유지. Hikari pending이 0인 구간이 많다. 이 구간의 500은 Load와 같이 “에러 없이, 풀은 가끔 참”.

**피크 5,000 (약 1:20–2:10)**  
VU가 1200 한도까지 차고 iteration은 drop된다. 완료량은 여전히 ~500 /s. pending은 159에 붙는다. 앱 5xx는 거의 없다.

**피크 후 500 (약 2:10–3:10)**  
목표 rate는 500으로 돌아온다. 완료량도 ~500 /s.  
그러나 VU는 1,100~1,200에 남고 pending은 1분 내내 157~159다.  
피크 전 같은 500 RPS가 VU 30 안팎이었던 것과 다르다. **처리량은 돌아왔지만 지연/대기는 1분 안에 안 풀렸다.**

**부하 0**  
k6가 끝나면 Hikari active/pending 0, health 200. 프로세스는 살아 있다.

## 회복

| 질문 | 답 |
| --- | --- |
| 피크에서 프로세스가 죽었는가 | 아니오. health 200 |
| 5,000 RPS를 소화했는가 | 아니오. drop + 풀 포화. 완료량은 ~500 |
| 500으로 내리면 Error는 잦아드는가 | 예. timeout은 거의 끝부분뿐 |
| 500으로 내리면 p95/pending이 피크 전으로 오는가 | 1분 관찰 구간에서는 아니오 |
| 부하를 끊으면 idle로 오는가 | 예. 수 초 안에 pending 0 |

500 RPS가 이미 천장 근처라, 피크에서 쌓인 대기 큐가 목표 500만으로는 빠지지 않는다. 커넥션 점유 시간이 길어진 상태(세션 행 증가, 큐잉)가 유지되면 40개 풀은 계속 풀가동이다.

## 분석

- Spike의 첫 병목도 Redis가 아니라 **Hikari + Tomcat 스레드 대기**다.
- 순간 5,000은 k6/앱/풀이 모두 거부한다. 거부 방식은 주로 drop과 대기이지 프로세스 크래시가 아니다.
- “회복”을 처리량만 보면 성공, 지연까지 보면 500 유지 부하에서는 미완이다. idle까지 내려야 풀이 비다.

## 결론

- Spike를 수행했고, 피크 중에도 앱은 살아 있다.
- 5,000 RPS는 이 구성의 한계를 넘는다. 완료량은 Load/Stress와 같은 ~500.
- 부하를 끊으면 바로 idle로 돌아온다.
- 500으로만 내리면 한도 근처라 pending이 남는다.
- 이번 Phase에서 구조를 바꾸지 않았다.
