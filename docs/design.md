# \[Playback Gate #2\] 요구사항 정의

## 1\. 시작하며

지난 글에서는 Playback Gate 프로젝트를 시작한 이유와 학습 목표를 정리했다.

이번에는 실제 구현에 들어가기 전에 **Playback Gate가 어떤 기능을 제공해야 하는지 요구사항을 정의**해보려고 한다.

이번 프로젝트의 목적은 완성도 높은 OTT 서비스를 만드는 것이 아니라 성능과 동시성 문제를 직접 경험하는 것이기 때문에 기능 범위는 최대한 단순하게 잡는다.

대신 이후 부하 테스트에서 의미 있는 문제가 발생할 수 있도록 **재생 권한 확인과 동시 재생 제한**을 핵심 기능으로 둔다.

---

# 2\. 서비스 범위

Playback Gate는 사용자가 콘텐츠의 재생을 요청했을 때 다음 질문에 답하는 서비스다.

> **이 사용자가 지금 이 콘텐츠를 재생해도 되는가?**

Playback Gate가 직접 영상을 전송하지는 않는다.

재생 가능 여부를 판단하고, 조건을 만족한 사용자에게 Playback Session과 Playback Token을 발급하는 것까지만 담당한다.

```
사용자
  ↓
재생 요청
  ↓
Playback Gate
  ↓
재생 가능 여부 판단
  ↓
Playback Session 생성
  ↓
Playback Token 발급
  ↓
재생 허용
```

실제 CDN, DRM, 영상 인코딩 및 스트리밍 기능은 이번 프로젝트 범위에서 제외한다.

---

# 3\. 주요 도메인

기능을 구현하기 위해 우선 다음 네 가지 데이터를 관리한다.

## 3.1 Member

서비스를 이용하는 회원이다.

회원은 다음 상태를 가질 수 있다.

```
ACTIVE
BLOCKED
WITHDRAWN
```

정상 상태인 ACTIVE 회원만 콘텐츠를 재생할 수 있다.

---

## 3.2 Subscription

사용자가 보유한 이용권이다.

초기에는 다음 세 가지 이용권을 사용한다.

```
BASIC
STANDARD
PREMIUM
```

이용권에 따라 접근 가능한 콘텐츠와 동시 재생 가능 기기 수가 달라진다.

이용권동시 재생 가능 수

| BASIC | 1 |
| --- | --- |
| STANDARD | 2 |
| PREMIUM | 4 |

이 숫자 자체가 중요한 것은 아니며, 이후 동시성 테스트를 위한 정책으로 사용한다.

---

## 3.3 Content

사용자가 재생할 콘텐츠다.

콘텐츠에는 최소한 다음 정보가 존재한다.

-   콘텐츠 제목
-   공개 상태
-   공개 시작일
-   공개 종료일
-   연령 등급
-   필요한 최소 이용권 등급

예를 들어 다음과 같은 콘텐츠가 있다고 가정할 수 있다.

```
제목: Sample Movie

상태: OPEN

연령 등급: 15

필요 이용권: STANDARD

공개 기간:
2026-08-01 ~ 2026-08-31
```

---

## 3.4 Playback Session

현재 사용자가 콘텐츠를 재생하고 있다는 상태를 나타낸다.

```
사용자
콘텐츠
기기
재생 시작 시간
세션 만료 시간
세션 상태
```

세션 상태는 우선 다음과 같이 단순화한다.

```
ACTIVE
ENDED
EXPIRED
```

동시 재생 가능 여부를 판단할 때 사용자의 ACTIVE Playback Session 수를 확인한다.

---

# 4\. 기능 요구사항

## FR-01. 콘텐츠 재생 요청

사용자는 특정 콘텐츠에 대한 재생을 요청할 수 있어야 한다.

```
POST /api/v1/playback/sessions
```

재생 요청에는 최소한 다음 정보가 포함된다.

```
{
  "contentId": 100,
  "deviceId": "iphone-001"
}
```

사용자 정보는 인증 정보를 통해 확인한다.

---

## FR-02. 회원 상태 확인

Playback Gate는 재생을 요청한 회원의 상태를 확인해야 한다.

```
ACTIVE
→ 재생 가능

BLOCKED
→ 재생 불가

WITHDRAWN
→ 재생 불가
```

정상 상태가 아닌 회원의 요청은 즉시 거절한다.

---

## FR-03. 콘텐츠 상태 확인

요청한 콘텐츠가 실제로 존재하고 현재 재생 가능한 상태인지 확인해야 한다.

다음 조건을 모두 만족해야 한다.

-   콘텐츠가 존재해야 한다.
-   콘텐츠 상태가 OPEN이어야 한다.
-   현재 시간이 콘텐츠 공개 기간에 포함되어야 한다.

```
availableFrom <= 현재 시간 <= availableUntil
```

---

## FR-04. 이용권 유효성 확인

사용자가 현재 유효한 이용권을 가지고 있는지 확인해야 한다.

다음과 같은 경우에는 재생을 허용하지 않는다.

-   이용권이 존재하지 않는 경우
-   이용권이 만료된 경우
-   이용권이 정지된 경우

---

## FR-05. 이용권 등급 확인

콘텐츠마다 필요한 최소 이용권 등급이 존재한다.

예를 들어 어떤 콘텐츠의 조건이

```
requiredPlan = STANDARD
```

라면 다음과 같이 처리한다.

```
BASIC
→ 재생 불가

STANDARD
→ 재생 가능

PREMIUM
→ 재생 가능
```

---

## FR-06. 연령 제한 확인

회원의 나이가 콘텐츠의 연령 등급보다 낮다면 재생을 허용하지 않는다.

예를 들어:

```
사용자 나이: 17세

콘텐츠 연령 등급: 18세

→ 재생 불가
```

---

## FR-07. 동시 재생 제한

이용권별로 동시에 유지할 수 있는 ACTIVE Playback Session 수를 제한한다.

예를 들어 BASIC 이용권 사용자가 이미 한 기기에서 콘텐츠를 재생하고 있다면:

```
현재 ACTIVE Session = 1

BASIC 최대 허용 = 1

↓

추가 재생 요청 거절
```

한다.

이 기능은 이후 **동시성 문제를 재현하기 위한 핵심 요구사항**이기도 하다.

---

## FR-08. Playback Session 생성

모든 재생 조건을 통과하면 새로운 Playback Session을 생성한다.

예:

```
sessionId
memberId
contentId
deviceId
status = ACTIVE
startedAt
expiresAt
```

---

## FR-09. Playback Token 발급

Playback Session 생성이 완료되면 사용자에게 Playback Token을 발급한다.

Token에는 최소한 다음 정보를 포함한다.

```
사용자 ID
콘텐츠 ID
Playback Session ID
기기 ID
Token 만료 시간
```

Playback Token은 이후 실제 영상 서버가 존재한다고 가정했을 때 재생 권한을 증명하기 위한 용도로 사용한다.

---

## FR-10. 재생 종료

사용자는 재생 중인 Playback Session을 종료할 수 있어야 한다.

```
DELETE /api/v1/playback/sessions/{sessionId}
```

재생이 종료되면 해당 Session의 상태를

```
ACTIVE

↓

ENDED
```

로 변경한다.

이후 해당 Session은 동시 재생 수 계산에서 제외한다.

---

## FR-11. 만료된 Session 처리

Playback Session에는 만료 시간이 존재한다.

정상적인 종료 요청이 발생하지 않더라도 만료 시간을 초과한 Session은 더 이상 동시 재생 중인 Session으로 판단하지 않는다.

```
현재 시간 > expiresAt

↓

EXPIRED
```

---

# 5\. 재생 요청 처리 순서

초기 버전에서는 다음 순서로 재생 요청을 처리한다.

```
재생 요청
    ↓
회원 조회
    ↓
회원 상태 확인
    ↓
콘텐츠 조회
    ↓
콘텐츠 상태 / 공개 기간 확인
    ↓
이용권 조회
    ↓
이용권 유효성 확인
    ↓
이용권 등급 확인
    ↓
연령 제한 확인
    ↓
현재 ACTIVE Session 조회
    ↓
동시 재생 제한 확인
    ↓
Playback Session 생성
    ↓
Playback Token 발급
    ↓
응답
```

초기에는 성능을 고려해 이 과정을 줄이지 않는다.

오히려 가능한 한 일반적인 구현으로 시작한 뒤, 이후 부하 테스트에서 어느 부분이 병목이 되는지 확인하는 것이 목적이다.

---

# 6\. 비기능 요구사항

기능 요구사항보다 이번 프로젝트에서 더 중요하게 다룰 부분이다.

## NFR-01. 정확성

트래픽이 증가하더라도 재생 정책은 항상 정확하게 적용되어야 한다.

특히 동시 재생 제한은 여러 요청이 동시에 발생하더라도 깨져서는 안 된다.

예를 들어 BASIC 이용권의 최대 동시 재생 수가 1이라면:

```
동시 요청 1건
동시 요청 10건
동시 요청 100건

↓

항상 ACTIVE Session <= 1
```

이어야 한다.

---

## NFR-02. Low Latency

Playback API는 사용자가 재생 버튼을 누른 직후 호출되는 API이므로 가능한 한 빠른 응답을 제공해야 한다.

단순히 평균 응답시간만 확인하지 않고 다음 지표를 함께 측정한다.

-   p50
-   p95
-   p99

프로젝트 초기에는 특정 목표값을 임의로 정하지 않는다.

먼저 V1의 성능을 측정해 Baseline을 확보하고, 이후 각 개선 단계에서 얼마나 변화했는지 비교한다.

---

## NFR-03. 처리량 측정

Playback Gate가 일정 시간 동안 얼마나 많은 요청을 처리할 수 있는지 측정할 수 있어야 한다.

주요 지표로 RPS(Requests Per Second)를 사용한다.

```
V1
↓

성능 측정
↓

개선
↓

동일한 조건으로 재측정
```

각 버전의 처리량 변화를 기록한다.

---

## NFR-04. 대규모 동시 요청 대응

동시에 많은 사용자가 재생 요청을 보내는 상황에서도 서비스가 가능한 범위 내에서 안정적으로 동작해야 한다.

k6를 이용하여 트래픽을 단계적으로 증가시키며 서버의 한계를 확인한다.

---

## NFR-05. 순간 트래픽 증가 대응

OTT 서비스에서는 스포츠 생중계나 인기 콘텐츠 공개 직후처럼 특정 시점에 재생 요청이 급격하게 증가할 수 있다.

따라서 다음과 같은 상황을 재현한다.

```
평상시 Traffic
      ↓
특정 시점
      ↓
Traffic 급증
      ↓
다시 정상 Traffic
```

Spike Test를 통해 이 과정에서 Latency와 Error Rate가 어떻게 변화하는지 확인한다.

---

## NFR-06. 성능 관측

성능 문제가 발생했을 때 원인을 확인할 수 있어야 한다.

다음과 같은 정보를 수집한다.

-   API 요청량
-   API Latency
-   Error Rate
-   CPU 사용량
-   Memory 사용량
-   JVM 상태
-   GC
-   DB Connection Pool
-   DB Query 실행시간
-   Redis 상태

단순히 서비스가 느려졌다는 사실만 확인하는 것이 아니라 **어느 부분에서 병목이 발생했는지를 추적할 수 있어야 한다.**

---

## NFR-07. 동일한 조건에서 성능 비교

성능 개선 전후의 테스트 조건은 가능한 한 동일하게 유지한다.

```
동일한 Hardware

동일한 데이터

동일한 k6 Scenario

동일한 요청량
```

을 기준으로 변경 전과 변경 후를 비교한다.

그래야 특정 기술을 적용한 것이 실제로 효과가 있었는지 판단할 수 있다.

---

# 7\. 이번 프로젝트에서 제외할 기능

프로젝트의 목적과 관계없는 기능이 많아지면 정작 성능 실험에 시간을 사용하기 어렵다.

따라서 다음 기능은 구현 범위에서 제외한다.

-   회원가입 UI
-   실제 결제 시스템
-   실제 영상 스트리밍
-   영상 업로드 및 인코딩
-   DRM
-   CDN 구축
-   콘텐츠 추천
-   검색
-   댓글
-   좋아요
-   시청 기록 분석
-   관리자 페이지
-   실제 모바일/웹 OTT UI

필요한 회원, 이용권, 콘텐츠 데이터는 API 또는 테스트 데이터로 생성한다.

---

# 8\. 초기 성공 조건

기본 구현 단계에서는 다음 조건을 만족하면 V1이 완성된 것으로 판단한다.

-   정상 회원이 콘텐츠를 재생할 수 있다.
-   비정상 회원의 재생 요청이 거절된다.
-   이용권이 없는 사용자의 요청이 거절된다.
-   이용권 등급이 부족하면 재생이 거절된다.
-   연령 제한을 만족하지 않으면 재생이 거절된다.
-   동시 재생 가능 수를 초과하면 재생이 거절된다.
-   정상적인 요청은 Playback Session을 생성한다.
-   정상적인 요청은 Playback Token을 반환한다.
-   재생 종료 시 Playback Session을 종료한다.

여기까지는 **기능적으로 정상 동작하는 것만 확인한다.**

성능 최적화는 하지 않는다.

---

# 9\. 정리

Playback Gate의 핵심 기능 자체는 단순하다.

```
재생 요청
   ↓
재생 권한 검증
   ↓
동시 재생 확인
   ↓
Playback Session 생성
   ↓
Playback Token 발급
```

하지만 이후에는 이 단순한 API에 점점 많은 요청을 발생시키면서 다음 질문에 답해볼 예정이다.

> 사용자가 많아지면 어디부터 느려질까?

> DB는 어느 정도까지 버틸 수 있을까?

> Cache를 적용하면 실제로 얼마나 빨라질까?

> 동시에 같은 계정으로 재생하면 동시 재생 제한은 정말 지켜질까?

> 트래픽이 갑자기 증가하면 어떤 지표가 가장 먼저 무너질까?

다음 글에서는 이번에 정의한 요구사항을 기반으로 **Playback Gate의 초기 구조와 데이터 모델을 설계**해보려고 한다.
